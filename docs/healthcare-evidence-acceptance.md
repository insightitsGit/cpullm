# Healthcare evidence acceptance boundary

This is an engineering acceptance protocol for evidence handling. It does not
certify diagnosis, prescribing, interactions, medication suitability, or source
truth. All current medication and patient examples are fictional. No real
patient data or live medical recommendations are used by the acceptance runner.

## Engineering checks implemented

The strict policy blocks learned generation and retains source text, document
identity, character offsets, full-chunk hash, tenant scope and snapshot time.
Acceptance covers exact numeric/unit fidelity, recognized paraphrase conflicts,
explicit negation and uncertainty, refusal of unsupported patient advice,
missing-record abstention, bounded batch accounting and proof retention.
Real database tests cover permissions, similarly named source boundaries,
historical corrections, and scan overflow. Exact calculations are separately
labeled and never described as safe doses or treatment recommendations.

An independent canonical whole-record lookup/Decimal calculator supplies the
local comparison. It has the same fictional source records and original
queries. Report supported-task success and nonanswer success separately;
neither an always-refuse system nor a correct hidden number counts as a full
answer. The saved dataset, runner revision and outputs must accompany scores.

## Clinical deployment gate: NOT SATISFIED

Before any clinical decision-support claim, the deploying organization needs:

1. Authoritative product/record versions, provenance, jurisdiction, effective
   dates and an explicit policy for stale, incomplete or withdrawn sources.
2. Independently reviewed clinical gold and representative patient contexts;
   these must not be generated by the same code being evaluated.
3. Defined intended use and exclusions, including populations, routes,
   formulations, allergies, interactions and missing context relevant to that use.
4. Independent clinical review of error severity, subgroup performance,
   uncertainty/refusal behavior, and the actual user-facing workflow.
5. A separately validated clinical rules service if diagnosis or treatment
   decisions are intended. Neither quotation nor arithmetic supplies these rules.
6. Access control, source-version/response retention, incident handling and
   change validation appropriate to the deployment.

The current library has no external clinical sign-off and cannot automatically
validate medical source truth. `clinical_validation=False` and
`source_truth_verified=False` must remain visible. The benchmark report must
state this gate remains open even if all synthetic engineering cases pass.
Regulatory suitability is not determined by this software test suite.

## Comparison status

The user chose the local deterministic baseline. The hosted model arm is
explicitly unrun; no hosted-model accuracy, superiority, cost or clinical
efficacy result may be inferred from this local comparison.
